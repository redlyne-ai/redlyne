# Test suite

A regression test bench for the Redlyne engine. It exists for one reason:
**to make refactoring safe**. Before you touch the engine (e.g. porting
the bash core to Python, fixing performance, adding cross-platform
support), this suite captures what the engine does today. After your
change, it tells you if the behavior is preserved.

## What it tests

The suite uses the **golden file** pattern: each fixture (a Python snippet
that exercises some vulnerability pattern) has a matching golden JSON
file with the engine's expected output. Tests fail if the actual output
doesn't match.

Three categories of tests:

- **Parity tests** (`test_parity.py`) — compare engine output to golden
  files. Catches regressions in detection logic, remediation patches,
  comments, imports.
- **Sanity tests** — verify no orphan/missing golden files (catch
  configuration drift).
- **Benchmark** (`benchmark.py`) — measure engine performance per snippet.
  Generates JSON snapshots you can diff over time to track perf changes.

## Quick start

```bash
# From the repo root
pip install pytest

# Run all parity tests (slow: ~20s per fixture)
pytest tests/

# Run a single fixture
pytest tests/test_parity.py::test_detection_parity[001_yaml_unsafe_load] -v

# Run only the sanity checks (fast, no engine invocation)
pytest tests/test_parity.py::test_no_orphan_golden_files \
       tests/test_parity.py::test_no_missing_golden_files -v
```

The first time you run the full suite, expect 2-3 minutes total: the
legacy bash engine takes ~15-20s per snippet, and there are 8 fixtures.

## Adding a new fixture

1. Create the Python file under `tests/fixtures/<category>/`. Use a
   numeric prefix (`010_`, `011_`...) for ordering. Reserve the `100+`
   range for safe code and edge cases.

2. Generate its golden file:

   ```bash
   python tests/regenerate_golden.py <category>/<name>.py
   ```

3. Verify the golden looks right (`cat tests/golden/<category>/<name>.json`).
   Commit both the fixture and the golden together.

4. Run the parity test for the new fixture to confirm:

   ```bash
   pytest tests/test_parity.py::test_detection_parity[<name>] -v
   ```

## Refactoring workflow

The suite is built to support large engine refactors safely:

1. **Before**: run `pytest tests/` — should be all green. Capture a
   baseline benchmark (`python tests/benchmark.py`) and commit the
   resulting `benchmarks/results/baseline.json` to track perf over time.

2. **During refactor**: change the engine, rerun `pytest tests/` after
   each significant change. Any test that fails is either a regression
   (fix it) or an intentional behavior change (regenerate golden, document
   in the commit).

3. **After**: rerun the benchmark and compare:

   ```bash
   python tests/benchmark.py --compare \
     benchmarks/results/baseline.json \
     benchmarks/results/<new-snapshot>.json
   ```

   Confirm the new engine is at least as fast as the old one (or document
   the trade-off if it's not).

## Regenerating golden files

If you intentionally change engine behavior (e.g. a rule's detection
output changes shape), regenerate the affected golden files:

```bash
# Regenerate everything (slow, ~20s per fixture)
python tests/regenerate_golden.py

# Regenerate one category
python tests/regenerate_golden.py detection

# Regenerate a single fixture
python tests/regenerate_golden.py detection/001_yaml_unsafe_load.py
```

Always review the diff of the regenerated golden files before committing.
A surprising diff is usually a bug, not a feature.

## CI

Parity tests run on every push and PR via GitHub Actions
(`.github/workflows/test.yml`):

- **Linux** + **macOS**, Python 3.10 / 3.11 / 3.12 — full parity suite.
- Benchmark only runs on push to `main`, results uploaded as artifacts
  (90-day retention) so you can compare across releases.

Windows joins the matrix once we add `windows-latest` to the workflow
matrix — the Python engine itself is fully portable, no shim required.

## Cross-platform notes

The Python engine is byte-equivalent across Linux, macOS, and Windows
(provided files are read with explicit `encoding="utf-8"`, which the
engine and the tests do consistently). Golden files are stable across
platforms and `test_python_engine.py` runs on every OS without any skip.

## Known engine behavior

A few things to keep in mind when reading engine output:

- The engine encodes code with `\n` as a literal separator (not actual
  newlines) in the `original_code` and `remediated_code` fields. The
  Remediation.js parser reverts this when applying the patch. Tests
  compare strings as-is.
- Status `safe` means the engine ran successfully and found no vulnerable
  pattern. Status `no_detection` means the engine ran but produced no
  output file at all (rare; happens with malformed input).
- Vulnerability categories in the golden file are sorted alphabetically.
  This is enforced by `run_engine.py` so tests are stable.

## Troubleshooting

**`ModuleNotFoundError: No module named 'redlyne_engine'`**
Run pytest from the repo root, not from inside `tests/`. The conftest
adds `launch_tool/` to `sys.path` automatically when run from root.

**`Python 3.10+ required`**
The engine uses match statement and PEP-604 union syntax. Older Python
versions need to be upgraded — `brew install python@3.12` on macOS,
`sudo apt install python3.12` on Linux, `python.org` installer on Windows.

**Engine timeout in tests**
The default timeout in `run_engine.py` is 120s. If you have a particularly
slow snippet, raise it with `run_engine(snippet, timeout_s=300)`.

**Golden file fails to compare on Windows**
Line endings (CRLF vs LF). Make sure your git config has
`core.autocrlf=input` so checkouts don't introduce CRLF noise.
